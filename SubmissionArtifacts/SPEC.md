# ProfTracker — Final Project Specification
**Version:** 0.5 (Week 8 — Finalized) | **Author:** Clay Tryon | **Course:** AI 410

---

## Project Overview

ProfTracker is a Windows desktop application for Marvel Rivals players with five integrated capabilities:

1. **Hero Proficiency Capture** (Sprint 1) — OCR-based screen capture reads hero level and XP from the game client and stores them in a local SQLite database.
2. **Hero Browser & XP Progress** (Sprint 1) — Scrollable hero roster with per-hero detail view and XP-to-Champion progress bars.
3. **Hero Wiki RAG** (Sprint 3) — Natural language chat interface answers questions about hero abilities by retrieving content from the Marvel Rivals Fandom wiki and generating answers via Groq.
4. **Wiki Auto-Sync** (Week 8) — One-click sync fetches the full live hero roster, animated icons, ability data, and team-up synergies from the Fandom wiki and rebuilds the RAG index automatically.
5. **Team-Ups & Training** (Week 8) — Dedicated tabs surface team composition synergies and hero-specific training recommendations derived from wiki data.

---

## Problem Statement

Marvel Rivals players track dozens of heroes across sessions and need things the game itself does not provide:
- A persistent record of proficiency progress across all heroes
- Quick in-app answers about hero abilities without alt-tabbing to a browser
- Always-current hero roster and icons that update when the game adds new heroes

ProfTracker addresses all three without cloud dependencies, subscriptions, or accounts.

## HITL (Human-in-the-Loop) Design

ProfTracker is an AI-assisted tool, not a fully autonomous agent. Every AI action has a defined human review or override point:

| AI Action | HITL Checkpoint |
|-----------|----------------|
| OCR capture reads level + XP from screen | Result appears in the real-time activity log immediately; user reviews each line before finishing the session |
| OCR produces an unreadable result | Capture fails with an error in the log; user can re-navigate in-game and press the hotkey again to retry |
| Manual entry fallback | The manual entry dialog lets the user type level and XP directly, overriding any OCR output |
| First-run wiki sync | First Run dialog runs sync automatically but shows a "Skip (use built-in roster)" button at all times; user can abort |
| Wiki sync (SYNC panel) | User explicitly clicks "SYNC FROM WIKI"; every downloaded/skipped/error item is shown in the scrollable log |
| RAG answer generation | Every answer includes the source URLs retrieved; user can open the wiki page to verify the answer |
| RAG index ingestion | User provides the URL; status label shows chunk count after each ingest so over-/under-indexing is visible |

## Observability Design

### Synchronous Operations (OCR Capture)
- **Activity log panel** (FR-009): each capture event appended in real time with hero name, detected level, XP, and PASS/FAIL status
- **Session summary**: after finishing a session the app navigates to the Heroes tab, implicitly showing what was captured

### Asynchronous Operations (QThread workers)
All async workers emit a three-argument `progress` signal `(current: int, total: int, message: str)` that drives:
- A `QProgressBar` updated to `current / total`
- A status label showing the current message
- A `QPlainTextEdit` log appending `[current/total] message` for each event

This pattern is consistent across `IngestWorker`, `QueryWorker`, and `SyncWorker`.

### Error Surfacing
- All worker `error` signals display a human-readable message in the UI (status label or chat panel)
- No error is silently swallowed — every exception path emits either `error` or appends to the log

### RAG Evaluation
- `Sprint3/evaluate.py` + `Sprint3/eval_queries.json` provide offline retrieval metrics (Hit Rate @k, MRR)
- Running `python Sprint3/evaluate.py` after an index change gives an immediate quality signal
- Results documented in `Sprint3/eval_report.md`

## RAG Architecture

### Ingestion Pipeline
```
User pastes Fandom wiki URL  (or wiki sync provides bulk URLs)
      │
      ▼
IngestWorker (QThread)
      │
      ▼
MediaWiki API (action=parse)   ←── returns full HTML without JS requirement
      │
      ├──▶ Revisions API (action=query&prop=revisions)
      │         │  raw wikitext → regex extracts: role, HP, difficulty, real name
      │         ▼
      │    Stats Document   ←── isolated chunk, no biographical noise
      │
      └──▶ Full HTML → strip tags → plain text Document
      │
      ▼
LlamaIndex NodeParser  (512 tokens, 64 overlap)
      │
      ▼
HuggingFace bge-small-en-v1.5  ←── local embedding model, ~90 MB
      │
      ▼
VectorStoreIndex (in-memory + disk persist to rag_index/)
```

### Query Pipeline
```
User types question
      │
      ▼
QueryWorker (QThread)
      │
      ▼
VectorIndexRetriever  (top-k = 3)
      │
      ▼
Groq Llama 3.3 70B  (temperature = 0.1, compact mode)
      │
      ▼
Answer + source URLs → Chat panel
```

## Tech Stack

| Layer | Technology |
|-------|-----------|
| GUI | PyQt6 6.6+ |
| OCR | EasyOCR + pytesseract |
| Storage | SQLite (hero data, `%APPDATA%`) |
| Wiki data | MediaWiki API (action=parse + revisions) |
| HTML parsing | BeautifulSoup4 |
| Chunking | LlamaIndex NodeParser (512 tok / 64 overlap) |
| Embeddings | HuggingFace bge-small-en-v1.5 (local) |
| Vector store | LlamaIndex VectorStoreIndex (disk-persisted) |
| LLM | Groq API — llama-3.3-70b-versatile |
| Async | PyQt6 QThread (all workers) |
| Packaging | PyInstaller (self-contained Windows exe) |
| CI | GitHub Actions (test + release workflows) |
| Env mgmt | uv |
